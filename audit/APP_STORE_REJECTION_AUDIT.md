# Potraces — App Store / Play Store Rejection Audit

_Multi-agent audit (9 dimensions, 61 agents, adversarially verified). Raw findings 52, kept 46, dropped as false-positive 6._

**Severity counts:** blocker 0 · high 5 · medium 9 · low 32

## HIGH (5)

### Priced subscription paywall unlocks paid tiers locally with NO in-app purchase when RevenueCat is unconfigured
- **Store:** both  |  **Guideline:** Apple 3.1.1 / 2.1 (App Completeness); Google Play Payments  |  **Verdict:** confirmed (was high)  |  _dim: apple-iap-payments_
- **Cause:** PaywallModal.handleContinue falls back to a LOCAL unlock (applyTier(paidTier)) whenever isBillingConfigured() is false. isBillingConfigured() returns false while EXPO_PUBLIC_RC_IOS_KEY is empty, and that key is not even present in .env.example — so a build shipped in the documented 'DORMANT until configured' state shows real prices (RM7.99/mo, 'cancel anytime', auto-renewal disclosure) and a Continue CTA that grants Premium with no App Store purchase sheet. A reviewer taps Continue and gets the paid tier for free = non-functional purchase UI presenting purchasable content without IAP.
- **Evidence:** src/components/common/PaywallModal.tsx:379-393 (if(isBillingConfigured()) purchaseTier … else applyTier(paidTier)); src/services/billing.ts:30-32 (isBillingConfigured returns false when RC key blank); .env.example has no EXPO_PUBLIC_RC_IOS_KEY/ANDROID_KEY line; billing.ts:1-14 header 'DORMANT until configured'.
- **Fix:** Before submitting: set EXPO_PUBLIC_RC_IOS_KEY (prod EAS secret), create the 5 products (potraces_basic_monthly, pro/premium monthly+yearly) + 3 entitlements + a RevenueCat offering, and verify the Purchases.purchasePackage path actually presents the StoreKit sheet. If billing won't be live at launch, gate the whole paywall behind isBillingConfigured() so no prices/CTA render when IAP is unavailable.

### AD_ID permission ships but is not declared (Play Advertising ID gate)
- **Store:** google  |  **Guideline:** Play Advertising ID policy / Data Safety  |  **Verdict:** confirmed (was blocker)  |  _dim: android-play-permissions-policies_
- **Cause:** com.google.android.gms.permission.AD_ID is present in the authoritative shipping manifest (injected by a transitive dep — most likely RevenueCat's play-services-ads-identifier and/or Firebase via the applied google-services plugin). Any app targeting API 33+ that includes AD_ID MUST answer 'Yes' to the Advertising ID question in the Data Safety form and complete the Advertising ID declaration, or Google's automated review rejects the release outright.
- **Evidence:** android/app/src/main/AndroidManifest.xml:18 (<uses-permission ... AD_ID/>); package.json:133 react-native-purchases; android/build.gradle:9 google-services plugin + app.json:84 googleServicesFile. AD_ID not found in any node_modules source manifest — it merges from a binary AAR.
- **Fix:** Decide if you actually use the advertising ID. If NOT (privacy.html says you don't share with advertisers): strip it with a `<uses-permission android:name="com.google.android.gms.permission.AD_ID" tools:node="remove"/>` entry (remove from the committed manifest too). If you DO (RevenueCat attribution/analytics): keep it and complete the Play Console Advertising ID declaration + tick 'Device or other IDs' in Data Safety.
- **Already mitigated:** None. No tools:node="remove" strip for AD_ID exists in the committed manifest, and there is no Data Safety/Advertising-ID declaration artifact in the repo. The permission is injected by RevenueCat + Firebase and left in place.

### Precise location (Stripe Terminal) collected but not in Data Safety / needs use justification
- **Store:** google  |  **Guideline:** Play Data Safety / Location permissions declaration  |  **Verdict:** confirmed (was high)  |  _dim: android-play-permissions-policies_
- **Cause:** ACCESS_FINE_LOCATION + ACCESS_COARSE_LOCATION ship (Stripe Terminal Tap-to-Pay requires them for card acceptance and Stripe transmits device location off-device for fraud/compliance). ### Collectz: cross-user UGC with no report AND no block mechanism
- **Store:** both  |  **Guideline:** Apple 1.2 (b)+(c); Google Play UGC policy  |  **Verdict:** overstated (was blocker)  |  _dim: ugc-moderation-safety_
- **Cause:** Collectz is real cross-user UGC: participant-entered and organizer-typed names, team names (any roster member can rename via renameTeam), event details_text/rules_text, organizer reject_note shown to the rejected user, plus uploaded proof images, club photos and profile avatars. All roster names + team names + event text are served to ANY unauthenticated caller who has the share code (collectz-join `view` runs verify_jwt=false and share codes are forwarded in group chats), and proof images/avatars are shown to the organizer and other roster viewers. There is no way to report a session/name/image and no way to block another user — a participant cannot block the organizer or another participant, and the organizer's only lever is removeParticipant + regenerateShareCode (which the removed person can defeat by rejoining via a re-shared link). A repo-wide grep for report/block/flag user-moderation UI returns zero matches.
- **Evidence:** supabase/functions/collectz-join/index.ts:9-14 (anon `view` returns session + roster by share_code, 'PUBLIC projection'); CollectzJoin.tsx:245-262 renderMember (names shown), :372-392 renameTeam (any member), :651-670 details_text/rules_text; CollectzDetail.tsx:448-460 & :1073-1092 proof-image view; Grep report.?(user|abuse|content|offensive)/block.?(user|abusive) over src/ = No matches
- **Fix:** Add an in-app 'Report' action on each roster row / session and on proof images that files to a moderation queue, and a 'Block user' action that hides a blocked user's content and prevents re-join. Commit to acting on reports within 24h (remove content + eject user). Server-side: track blocks so a regenerated/forwarded link still enforces them.
- **Already mitigated:** Partial mitigations only: share codes are unguessable and brute-force-rate-limited (MISS_LIMIT/MISS_WINDOW, collectz-join/index.ts:48-52,132-142); anon `view` withholds proofs and user_ids ("PUBLIC projection", line 12); proof images are organizer-only (1:1), not roster-broadcast; organizer can removeParticipant + regenerateShareCode. None of these constitute an in-app report mechanism or a user-block mechanism, which do not exist.

## MEDIUM (9)

### Bluetooth (Always+Peripheral) and LocalNetwork strings describe external card readers the app never connects to
- **Store:** apple  |  **Guideline:** Apple 5.1.1 (permission purpose string must match actual use)  |  **Verdict:** overstated (was medium)  |  _dim: ios-permissions-tracking_
- **Cause:** The purpose strings say Bluetooth/WiFi are used 'to connect to supported card readers', but the code only ever calls easyConnect with discoveryMethod:'tapToPay' (tapToPay.ts:173) — the built-in iPhone NFC reader, which uses neither Bluetooth nor the local network. External-reader discovery (bluetoothScan / internet / localMobile) is never invoked, so even with Tap to Pay fully enabled these three prompts never fire. NSBluetoothAlwaysUsageDescription (background BLE) is the least justified of all — Tap to Pay needs no background Bluetooth.
- **Evidence:** tapToPay.ts:167-186 (connectTapToPayReader only uses discoveryMethod:'tapToPay'); ios/Potraces/Info.plist:93-96 (NSBluetoothAlways/Peripheral = 'connect to supported card readers'); Info.plist:103-104 (NSLocalNetwork = 'connect to supported card readers')
- **Fix:** Drop NSBluetoothAlwaysUsageDescription entirely (no background BLE use). If Tap to Pay ships, keep only what the Stripe Terminal SDK strictly requires to build; the app's tapToPay-only flow does not exercise Bluetooth or LocalNetwork prompts, so prefer removing them with the plugin per the prior finding.
- **Already mitigated:** These three strings are the Stripe Terminal official Expo config plugin's own DEFAULT purpose strings. withStripeTerminalIos() unconditionally writes NSBluetoothAlwaysUsageDescription / NSBluetoothPeripheralUsageDescription / NSLocalNetworkUsageDescription on every prebuild, and the exact "...connect to supported card readers" wording is the plugin's `||` default (app.json only supplied locationWhenInUsePermission). They are vendor-standard strings shipped by the entire Stripe Terminal iOS ecosystem, which Apple accepts. The StripeTerminal 5.5.0 pod links CoreBluetooth/local-network for its non-Tap-to-Pay reader types, so these strings guard the linked frameworks; removing NSBluetoothAlwaysUsageDescription (the claim's fix) risks a missing-purpose-string rejection, not a fix. Background BLE is NOT enabled: UIBackgroundModes 'bluetooth-central' is only added when the bluetoothBackgroundMode prop is set, and it is not.
