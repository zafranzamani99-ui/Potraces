## 🧭 The core decision (don't blur these two things)
There are **two** different "AI + Potraces" ideas. They pull in opposite directions:

- **Thing B — the AI works *inside* Potraces** (chat + calculations, powered by Claude/Gemini under the hood). **This is Echo. It is CORE / near-term, NOT v1.2.** Here we own the customer, the habit, the data, and the billing; the model is a swappable commodity. Improving Echo's finance chat + calc is tracked with Echo work, **not here.**
- **Thing A — Potraces is *reachable from* the assistant** (user chats in ChatGPT/Claude, it pulls their numbers from Potraces via MCP). **THIS is v1.2.** It's a **reach / distribution** play, not the home.

**Guiding rule:** _Let the AI work inside Potraces now (own it); let Potraces be reachable from the assistants later (a doorway, not a home). Never put billing or brand on someone else's platform._

---

## 🚦 The two gates (both must be TRUE before building A)
Building this before these are true = effort spent on a near-empty channel.
1. **There is a ledger worth querying.** Enough captured history + corrections that "ask ChatGPT about your Potraces data" actually returns something valuable. (Depends on the v1.0 beachhead working.)
2. **Assistant usage in Malaysia has meaningfully grown.** Today almost no Malaysian does their finances in ChatGPT/Gemini (market is Android + WhatsApp + e-wallet, price-sensitive). Revisit when that shifts.

_Owner check-in: review these gates ~quarterly post-launch; don't start until both read yes._

## 🔒 Design principles (locked, if/when we build it)
- **Read-only first.** Expose query tools (spending summary, transactions, budget status), **not** write/move-money tools. Consistent with the app-wide "never move money, only read + draft" rule.
- **Explicit opt-in, scoped, revocable.** OAuth 2.1, user turns it on per-assistant, can revoke. Never default-on. Market it as "you're in control."
- **Billing stays in Potraces.** No assistant has an in-app subscription rail (verified in the integration research). MCP is **top-of-funnel back into the app**, never the paywall.
- **Privacy caveat — this cuts against a moat.** Piping a Malaysian's full ledger to OpenAI/Google weakens the "we don't sell your data" positioning. So: consented, scoped, minimal, and clearly disclosed. If in doubt, keep it off.
- **Be reachable, stay owned.** The assistant supplies the interface; Potraces keeps the data, the actions, and the relationship.

## 🧱 Build sketch (cheap — reuses what exists)
_Reference: MCP is one server that reaches ChatGPT (Apps SDK is built on MCP), Claude, Gemini, Kimi.
Monarch already does this pattern for a PFM. Effort ≈ days-to-weeks, backend-only._
- [ ] 🔴 Stand up **one MCP server** wrapping the **existing** Potraces data API (Supabase) — no app rewrite.
- [ ] 🟢 Expose **read-only tools**: `get_spending_summary`, `list_transactions`, `get_budget_status`, (seller) `get_profit_summary`. Reuse the same query layer that feeds the app.
- [ ] 🔴 **OAuth 2.1** so the assistant acts on the right user's account, scoped read-only.
- [ ] 🟢 In-app **consent screen** ("Connect Potraces to ChatGPT/Claude — read-only, you can revoke").
- [ ] 🟡 **Data-safety / privacy-policy update** to disclose the optional third-party assistant connection.
- [ ] 🟢 (optional) A ChatGPT **App** UI widget (a spending chart) — incremental over the plain MCP server.
- [ ] 🟡 Test invocation from Claude + ChatGPT; confirm the model actually calls our tools (discovery is opaque — being listed ≠ being called).
